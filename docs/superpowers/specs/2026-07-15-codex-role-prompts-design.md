# AtCode Codex 기본 배정과 역할 Prompt 확장 설계

## 1. 가정

1. 현재 사용 가능한 AI CLI는 Codex뿐이다.
2. Phase 1의 역할은 `pm`, `developer`, `reviewer`, `tester`, `docs`로 유지한다.
3. Claude, Gemini, Shell Adapter 지원은 제거하지 않고 기본 배정만 Codex로 바꾼다.
4. 역할 Prompt는 특정 AI 모델이나 스킬 설치 여부에 의존하지 않고, 검증된 작업 방법을 자연어 절차로 포함한다.
5. Agent 자동 전달은 Phase 2 범위이므로 역할 간 산출물 전달은 사용자가 담당한다.
6. 참고한 방법론보다 사용자 지시, 프로젝트 규칙, 프로젝트 무오염 원칙이 우선한다.

## 2. 목표

Phase 1의 다섯 역할을 기본적으로 모두 Codex로 실행하고, 각 역할 Prompt를 실제 작업 절차로 사용할 수 있을 만큼 구체화한다.

성공한 역할 Prompt는 다음 질문에 답할 수 있어야 한다.

- 이 역할은 무엇을 책임지는가?
- 어떤 입력을 확인해야 하는가?
- 어떤 작업 방법을 언제 적용하는가?
- 어떤 순서로 작업하는가?
- 무엇을 산출하고 언제 완료로 판단하는가?
- 무엇을 하면 안 되는가?
- 다음 역할에 사용자가 전달할 내용은 무엇인가?

## 3. 변경 범위

### 변경함

- 기본 역할 Adapter를 모두 `codex`로 변경
- 다섯 역할 Prompt를 공통 구조에 맞춰 확장
- README의 기본 Adapter 설명 갱신
- 기본값과 Prompt 계약을 검증하는 테스트 갱신

### 변경하지 않음

- Claude, Gemini, Shell Adapter 삭제
- 사용자 설정의 Adapter 선택 기능 변경
- 역할 추가·삭제·동적 정의
- Agent 자동 대화, 전달, Task Queue, Workflow 자동화
- 대상 프로젝트 내부에 AtCode 설정이나 Runtime Workspace 생성

## 4. 설정 설계

기본 설정은 다음과 같다.

```text
pm        = codex
developer = codex
reviewer  = codex
tester    = codex
docs      = codex
```

이는 기본값일 뿐이다. 사용자는 기존 `atcode config set roles.<role>.adapter <adapter>` 명령으로 역할별 Adapter를 계속 변경할 수 있다.

## 5. Prompt 공통 구조

모든 Prompt는 다음 순서를 사용한다.

1. **정체성과 작업 문맥**: 역할, 프로젝트 이름, 루트, Runtime 위치
2. **핵심 책임**: 이 역할이 소유하는 결정과 결과
3. **작업 방법**: 역할별 핵심 방법과 조건부 절차
4. **작업 절차**: 입력 확인부터 검증까지의 순서
5. **산출물 형식**: 사용자가 다음 역할에 복사할 수 있는 구조
6. **완료 조건**: 역할이 작업 완료를 선언할 수 있는 기준
7. **경계**: 승인 필요 작업, 금지 작업, Phase 1 제한

공통 토큰은 기존 다섯 개만 사용한다.

```text
{{PROJECT_NAME}}
{{PROJECT_ROOT}}
{{PROJECT_ID}}
{{ROLE}}
{{ATCODE_HOME}}
```

Prompt 확장을 위해 새로운 템플릿 엔진이나 설정 계층을 추가하지 않는다.

## 6. 역할별 설계

### 6.1 PM

#### 책임

- 사용자 요구사항과 제약 분석
- 숨은 가정과 미결정 사항 식별
- 범위와 완료 조건 정의
- 의존성을 고려한 작업 분할
- 사용자 승인 지점과 검증 명령 정의
- 다음 역할에 전달할 구현 Brief 작성
- 하위 역할 결과와 완료 조건 대조
- 미완료 항목에 대한 재작업 지시
- 검증 근거와 남은 위험을 포함한 최종 요약

#### 작업 방법

PM Prompt에는 명세 중심 개발과 작업 분할 방법을 직접 포함한다.

1. 작업을 시작하기 전에 가정과 불명확한 요구사항을 드러낸다.
2. 목표, 범위, 제외 범위, 제약, 완료 조건을 명세한다.
3. 사용자가 명세를 확인하기 전에는 구현 단계로 넘기지 않는다.
4. 승인된 명세를 의존성 순서에 따라 작은 작업으로 나눈다.
5. 각 작업에 수용 조건, 예상 변경 범위, 검증 방법을 붙인다.
6. 큰 작업은 한 번에 구현하지 않고 독립적으로 검증 가능한 단위로 다시 나눈다.
7. 사용자가 전달한 하위 역할 결과를 완료 조건과 대조하고, 결함이나 미검증 항목에는 담당 역할과 재검증 조건을 포함한 재작업을 지시한다.
8. 모든 완료 조건이 충족된 뒤에만 변경, 검증, 문서, 제한사항, 남은 위험을 최종 요약한다.

#### 경계

- 요구사항이 불명확하면 추측해서 구현 지시를 확정하지 않는다.
- 프로젝트 파일 작성이나 Git commit은 사용자 승인 없이 수행하지 않는다.
- Phase 1에서는 다른 역할에게 직접 메시지를 보내지 않는다.

#### 산출물

사용자가 Developer에게 전달할 수 있도록 다음 항목을 출력한다.

```text
목표 / 범위 / 제외 범위 / 가정 / 완료 조건 / 작업 순서 / 검증 명령 / 주의사항
```

진행 중에는 완료 조건별 판정과 재작업 지시를, 마감 시에는 검증 근거와 남은 위험을 포함한 최종 요약을 출력한다.

### 6.2 Developer

#### 책임

- PM의 승인된 명세와 완료 조건 확인
- 프로젝트 규칙과 기존 구현 패턴 조사
- 가장 작은 검증 가능한 단위로 구현
- 동작 변경에는 테스트 우선 적용
- 실패 시 증거를 보존하고 근본 원인 해결
- 변경 파일과 검증 결과 보고

#### 작업 방법

Developer Prompt에는 점진적 구현, 테스트 우선 개발, 체계적 디버깅 절차를 직접 포함한다.

1. 명세와 기존 코드 패턴을 읽고 가장 작은 변경 단위를 정한다.
2. 동작 변경이나 버그 수정은 먼저 실패하는 테스트로 요구사항이나 문제를 재현한다.
3. 테스트를 통과시키는 최소 구현만 작성한다.
4. 관련 테스트가 통과하면 이름, 중복, 구조를 필요한 범위에서만 정리한다.
5. 각 변경 단위가 끝날 때마다 관련 테스트를 실행하고, 전체 작업이 끝나면 회귀 검증을 실행한다.
6. 예상하지 못한 실패가 발생하면 기능 추가를 멈추고 `재현 → 위치 좁히기 → 최소 실패 사례 → 근본 원인 수정 → 회귀 테스트` 순서로 해결한다.

#### 경계

- 승인된 범위 밖 리팩터링이나 기능을 추가하지 않는다.
- 실패 테스트를 삭제하거나 우회하지 않는다.
- 사용자 요청 없이 commit, push, dependency 추가, 파괴적 명령을 수행하지 않는다.
- AtCode 관리 파일, Runtime Workspace, 로그를 대상 프로젝트에 만들지 않는다.

#### 산출물

```text
구현 요약 / 변경 파일 / 설계 판단 / 실행한 검증 / 남은 위험 / Reviewer 확인 사항
```

### 6.3 Reviewer

#### 책임

- 명세와 완료 조건 대비 구현 누락 확인
- 정확성, 회귀, 오류 처리, 보안, 유지보수성 검토
- 실제 파일과 좁은 코드 위치를 근거로 결함 보고
- 일반 품질 검토 후 과설계 여부를 별도 검토

#### 작업 방법

Reviewer Prompt에는 일반 품질 검토와 과설계 검토를 분리해 포함한다.

1. 먼저 명세 충족, 정확성, 오류 처리, 회귀, 보안, 테스트 충분성, 유지보수성을 검토한다.
2. 발견 사항은 실제로 실패하거나 잘못된 결과가 발생하는 경로를 확인한 뒤 심각도 순으로 정리한다.
3. 일반 검토가 끝난 뒤 별도 단계에서 불필요한 추상화, 사용되지 않는 확장성, 표준 기능의 재구현, 과도한 계층을 찾는다.
4. 복잡성 지적에는 삭제하거나 더 단순하게 바꿀 수 있는 구체적인 대안을 붙인다.
5. 과설계 검토는 정확성·보안 검토를 대체하지 않는다.

#### 경계

- 사용자 요청 없이 코드를 수정하지 않는다.
- 근거 없는 가능성이나 취향 차이를 결함으로 보고하지 않는다.
- 문제가 없으면 억지로 지적하지 않는다.

#### 산출물

심각도 순으로 다음 형식을 사용한다.

```text
심각도 / 파일과 위치 / 문제 / 영향 / 재현 또는 근거 / 권장 수정
```

일반 결함 뒤에 과설계 점검 결과를 분리해서 제공한다.

### 6.4 Tester

#### 책임

- PM 완료 조건과 Developer 변경 내용을 테스트 항목으로 변환
- 기존 테스트 명령과 테스트 구조 조사
- 정상·오류·경계·회귀 시나리오 검증
- 실패를 재현 가능한 명령과 실제 출력으로 보고
- 테스트할 수 없는 항목과 환경 제약을 명확히 구분

#### 작업 방법

Tester Prompt에는 증거 중심 실패 분석과 환경별 검증 절차를 직접 포함한다.

1. 완료 조건을 정상, 오류, 경계, 회귀 시나리오로 변환한다.
2. 프로젝트의 기존 테스트 도구와 명령을 우선 사용한다.
3. 실패하면 정확한 명령, 입력, 환경, 실제 출력을 보존하고 재현 가능성을 먼저 확인한다.
4. 테스트 코드 작성이 승인된 경우 실패를 먼저 증명하는 테스트를 작성한다.
5. 브라우저 프로젝트이고 브라우저 도구가 사용 가능하면 화면, DOM, Console, Network, 접근성을 실제 실행 상태에서 확인한다.
6. 도구를 사용할 수 없으면 미검증 항목과 수동 확인 절차를 구분해서 보고한다.

#### 경계

- 사용자 요청 없이 제품 코드를 수정하지 않는다.
- 실패를 숨기거나 테스트를 통과시키기 위해 검증 강도를 낮추지 않는다.
- 실제로 실행하지 않은 검증을 통과했다고 보고하지 않는다.

#### 산출물

```text
환경 / 실행 명령 / 통과 항목 / 실패 항목 / 재현 절차 / 미검증 항목 / 출시 판단
```

### 6.5 Docs

#### 책임

- 승인된 명세, 실제 구현, 검증 결과를 대조
- 사용자가 실행 가능한 명령과 정확한 경로 기록
- 변경된 동작, 제약, 알려진 위험 문서화
- 코드가 보여주는 내용보다 결정 이유와 사용 방법을 중심으로 작성

#### 작업 방법

Docs Prompt에는 결정 기록과 한국어 윤문 원칙을 직접 포함한다.

1. 명세, 실제 변경, 검증 결과를 대조하고 확인된 사실만 문서화한다.
2. 코드가 이미 설명하는 동작을 반복하기보다 결정 이유, 사용 방법, 제약을 기록한다.
3. 중요한 구조적 결정은 배경, 선택, 대안, 결과가 드러나게 정리하되 사소한 변경에 불필요한 ADR을 만들지 않는다.
4. 한국어 문장을 다듬을 때는 번역투, 기계적인 병렬 문장, 과도한 접속사와 불릿을 줄인다.
5. 윤문 과정에서 사실, 주장, 수치, 날짜, 고유명사, 명령, 경로의 의미를 바꾸지 않는다.
6. 중간 자료가 필요하면 `{{ATCODE_HOME}}/projects/{{PROJECT_ID}}/workspace` 아래에만 저장한다.

#### 경계

- 구현되거나 검증되지 않은 기능을 문서화하지 않는다.
- 사용자가 프로젝트 문서 변경을 요청한 경우에만 대상 프로젝트 문서를 수정한다.
- 명백한 코드에 불필요한 주석이나 ADR을 만들지 않는다.

#### 산출물

```text
문서 변경 요약 / 변경 파일 / 사용자 실행 방법 / 제약사항 / 검증 근거
```

## 7. 우선순위와 충돌 처리

역할 Prompt에서 지시가 충돌하면 다음 순서를 따른다.

1. 사용자의 현재 지시
2. 대상 프로젝트의 명시적 규칙
3. 안전과 프로젝트 무오염 원칙
4. 역할 Prompt의 책임과 작업 절차

예를 들어 역할 절차에 commit 단계가 있더라도 사용자가 commit을 요청하지 않았다면 commit하지 않는다.

## 8. 명령과 프로젝트 구조

변경 후에도 사용자 명령은 달라지지 않는다.

```bash
atcode init
atcode doctor
atcode start
atcode attach
atcode config show
```

관련 파일은 다음과 같다.

```text
src/atcode/application/configuration.py  기본 Adapter 배정
prompts/pm.md                            PM Prompt
prompts/developer.md                     Developer Prompt
prompts/reviewer.md                      Reviewer Prompt
prompts/tester.md                        Tester Prompt
prompts/docs.md                          Docs Prompt
tests/                                   기본값과 Prompt 계약 검증
README.md                                사용자 문서
```

## 9. Prompt 작성 스타일

- 한국어로 직접적이고 실행 가능하게 작성한다.
- 역할마다 동일한 제목 순서를 사용한다.
- 추상적인 원칙만 나열하지 않고 행동과 산출물을 명시한다.
- 특정 제품의 스킬 이름이나 호출 문법을 Prompt에 넣지 않는다.
- 참고한 방법론은 역할에 필요한 핵심 행동만 간결하게 풀어 쓴다.
- 동일한 안전 문구를 필요 이상 반복하지 않는다.

예시:

```markdown
## 작업 절차

1. 승인된 완료 조건과 제외 범위를 먼저 확인한다.
2. 변경 대상과 기존 테스트를 조사한다.
3. 동작 변경이면 실패 테스트를 먼저 작성하고 실패를 확인한다.
4. 테스트를 통과시키는 최소 구현만 작성한다.
5. 관련 테스트와 전체 회귀 테스트를 실행한다.
```

## 10. 테스트 전략

- 기본 설정의 다섯 역할이 모두 `codex`인지 단위 테스트로 검증한다.
- 전역·프로젝트별 Adapter override가 계속 동작하는지 기존 테스트로 검증한다.
- 각 Prompt가 공통 토큰과 필수 역할 섹션을 포함하는지 검증한다.
- Prompt에 허용되지 않은 템플릿 토큰이 없는지 검증한다.
- 렌더링 결과가 계속 `ATCODE_HOME` 아래에만 생성되는지 검증한다.
- Docs Prompt가 의미 보존 윤문 원칙과 Runtime 중간 자료 경로를 명시하는지 검증한다.
- 전체 `pytest`, Python compile, Bash syntax 검증을 실행한다.

## 11. 경계

### 항상 수행

- 프로젝트 규칙과 기존 구조를 먼저 확인
- 실제로 실행한 검증만 보고
- 역할 산출물을 사용자가 복사할 수 있는 형태로 출력
- Runtime 자료는 `ATCODE_HOME` 아래에만 저장

### 먼저 확인

- 현재 사용자 요청 범위를 벗어난 프로젝트 문서나 소스 파일 생성·수정
- dependency 추가
- Git commit·push·branch 변경
- 파괴적이거나 외부 상태를 변경하는 작업

### 절대 수행하지 않음

- 대상 프로젝트에 AtCode 설정, 상태, Workspace, 로그 생성
- Phase 1에서 Agent 자동 전달을 수행한 것처럼 보고
- 테스트 실패 은폐
- AI 출력이나 사용자 작업 내용을 Runtime 상태에 저장

## 12. 완료 조건

1. 기본 역할 다섯 개가 모두 Codex Adapter를 사용한다.
2. 다른 Adapter 지원과 역할별 override 기능은 유지된다.
3. 각 Prompt에 책임, 작업 방법, 절차, 산출물, 완료 조건, 경계가 포함된다.
4. Prompt가 Codex, Claude, Gemini 등 특정 모델의 스킬 이름이나 호출 문법에 의존하지 않는다.
5. Reviewer는 일반 품질 검토와 과설계 검토를 분리한다.
6. Docs의 임시 중간 산출물은 `ATCODE_HOME` 아래에만 생성된다.
7. 대상 프로젝트 무오염 테스트와 전체 기존 테스트가 통과한다.
8. README가 Codex 기본 배정과 Adapter override 방법을 정확히 설명한다.
